First 10 commands

A beginner path from an empty folder to a pushed project.

git init -b main

# 2. See what changed
git status

# 3. Stage files

# 4. Save a snapshot

# 5. See the history
git log --oneline

git push -u origin main

# 10. Download updates later
git pull

Do steps 6 and 7 after you made at least one commit on the new branch. Practice them safely in the "Practice exercises" section.

The four areas of Git

Every change moves through the same places. Each command moves changes from one area to another.

  • Working directory: the files you edit.
  • Staging area (index): the changes selected for the next commit.
  • Local repository: your commits, stored in .git.
  • Remote repository: the shared copy on a host such as GitHub.

Concepts

What is Git?

Git is a distributed version control system for tracking changes in files and collaborating on code. It was created by Linus Torvalds in 2005 and has been maintained by Junio Hamano since then.

What does Git do?

  • Manage projects with repositories
  • Clone a project to work on a local copy
  • Track changes with staging and committing
  • Branch and merge to work on different parts and versions of a project
  • Pull the latest version of the project into a local copy
  • Push local updates to the main project

Why Git?

  • It is the most widely used version control system (over 90% of developers in recent Stack Overflow surveys).
  • Developers can work together from anywhere in the world.
  • The full history of the project is available locally.
  • Any earlier version of the project can be restored.

Difference between Git and GitHub

Git is a tool installed locally that tracks changes to source code and manages versions in a repository.

GitHub is a web-based hosting service for Git repositories. It adds collaboration features on top of Git, such as pull requests, issues, code review and CI (GitHub Actions).

Alternatives to GitHub

  • GitLab
  • Bitbucket
  • Azure DevOps Repos
  • Gitea
  • GitBucket
  • SourceForge
  • Launchpad
  • Assembla

GitLab vs GitHub

  • Both offer free plans, including private repositories.
  • GitLab has a free, self-hostable Community Edition and built-in CI/CD and DevOps tooling.
  • GitHub has the largest community and ecosystem, and uses GitHub Actions for CI/CD.

Repository

A repository (repo) is a collection of files and directories managed by Git. It holds the project's files and its full history: what changed, who changed it, and when.

  • Local repository: the copy that exists on your computer.
  • Remote repository: a copy hosted on a server or service such as GitHub, GitLab or Bitbucket.

Git directory

The hidden .git directory stores all the metadata and the object database of a repository. Deleting it removes the repository history.

File states

  • Untracked: a file Git is not tracking. It is not in the history or in commits.
  • Tracked: a file Git knows about and monitors for changes.
  • Unstaged: changes in the working directory not yet added with git add.
  • Staged: changes added to the staging area, ready for the next commit.
  • Snapshot: each commit is a snapshot of the project at a point in time.

Merge

Combine the changes of another branch into the current branch.

Resolve merge conflicts

  1. Run git status to see the conflicted files.
  2. Edit each file and resolve the <<<<<<<, ======= and >>>>>>> markers.
  3. Stage the resolved files, then finish the merge.
git add <file>
git commit

Cherry-pick

Apply one or more specific commits from another branch onto the current branch.

  • Use it when you committed to the wrong branch, or need just one or two commits.
  • Use git merge instead when you want the whole branch.
git cherry-pick <commit-id>
git cherry-pick 776a7cb605b5f1281f963ea39f70a194f15a92b1

Find which branch a branch was created from

git reflog show --no-abbrev <branch-name>

Rebase

Replay your commits on top of another branch for a linear history.

git rebase <branch-name>
git rebase --continue
git rebase --abort

Do not rebase commits that are already pushed and shared.

Move a branch onto a new base (--onto)

Take only the commits after <old-base> and replay them on <new-base>. Useful when a branch was started from another feature branch.

git rebase --onto <new-base> <old-base> <branch>
git rebase --onto main feature-a feature-b

Update the branches of a stack together (2.38+)

git rebase --update-refs main
git config --global rebase.updateRefs true

Undo changes

Discard local changes

Discarded changes cannot be recovered.

Discard unstaged changes in a file

git restore <file>
git checkout -- <file>

Discard all unstaged changes

git restore .
git checkout -- .

Unstage a file (keep the changes)

git restore --staged <file>

Reset a file or the whole working directory to the last commit

git restore --source=HEAD --staged --worktree <file>
git checkout HEAD -- <file>
git checkout HEAD -- .

Revert

git revert undoes a commit by creating a new commit with the opposite changes. It is safe for shared history.

git revert <commit-id>

Reset

Move the current branch to another commit.

# Undo the last commit, keep changes staged
git reset --soft HEAD~1

# Undo the last commit, keep changes unstaged (default)
git reset HEAD~1

# Undo the last commit and delete its changes
git reset --hard HEAD~1

--hard deletes uncommitted work. Avoid resetting commits that are already pushed.

Clean untracked files

-f (force) is required to delete. -d also removes untracked directories. Preview first with -n (dry run).

git clean -nd
git clean -fd

Reflog

Shows where HEAD has been, which helps to recover lost commits after a reset or a bad rebase.

git reflog
git reset --hard HEAD@{n}

Workflows and advanced

Branching strategies

  • GitHub Flow: main is always deployable. Create a short-lived feature branch, open a pull request, review, merge, deploy. Best for most teams and continuous delivery.
  • Trunk-based development: everyone commits to main (or very short-lived branches) several times a day, using feature flags and strong CI. Best for fast, mature teams.
  • Git Flow: long-lived main and develop branches plus feature/*, release/* and hotfix/*. Best for versioned releases, but heavier to maintain.

Common branch naming

feature/login-page
bugfix/null-user-error
hotfix/payment-timeout
release/1.4.0

Commit message conventions

Conventional Commits makes history readable and lets tools generate changelogs and version numbers.

<type>(<optional scope>): <description>

[optional body]

[optional footer]

Common types

feat      a new feature (minor version bump)
fix       a bug fix (patch version bump)
docs      documentation only
style     formatting, no code change
refactor  code change that neither fixes a bug nor adds a feature
perf      performance improvement
test      add or fix tests
build     build system or dependencies
ci        CI configuration
chore     other maintenance
revert    revert a previous commit

Examples

git commit -m "feat(auth): add password reset"
git commit -m "fix(cart): handle empty cart on checkout"
git commit -m "feat!: drop support for PHP 7"
  • A ! after the type, or a BREAKING CHANGE: footer, marks a breaking change (major version bump).
  • Keep the subject around 50 characters, in the imperative mood ("add", not "added"), without a trailing period.
  • Use the body to explain why, not what.

Interactive rebase

Edit, reorder, combine or remove the last commits before sharing them.

git rebase -i HEAD~3
git rebase -i <commit>^

Commands in the to-do list

Fixup and autosquash

Create a commit marked as a fix for an earlier commit, then let Git fold it in automatically.

git commit --fixup=<commit>
git rebase -i --autosquash <commit>^

Always autosquash with interactive rebase

git config --global rebase.autoSquash true

Newer Git versions can do this in one step with git history fixup (see "What's new").

Pull request workflow

git switch main
git pull
git switch -c feature/my-change
# edit files, then
git add .
git commit -m "feat: describe the change"
git push -u origin feature/my-change
  1. Open a pull request on the host (or run gh pr create).
  2. Address review comments by pushing more commits to the same branch.
  3. Merge when approved and checks pass, then delete the branch.

Merge options

  • Merge commit: keeps all commits and adds a merge commit.
  • Squash and merge: turns the whole branch into one commit. Clean history, loses individual commits.
  • Rebase and merge: replays commits on top of the base branch for a linear history.

git branch -d feature/my-change

Bisect

Binary search through history to find the commit that introduced a bug.

git bisect start
git bisect bad
git bisect good <commit-or-tag>
# Git checks out a middle commit. Test it, then run
git bisect good
git bisect bad
# when finished
git bisect reset

Automate with a script that exits 0 for good and non-zero for bad

git bisect start <bad> <good>
git bisect run ./test.sh

Worktree

Check out several branches at the same time in separate folders that share one repository. Useful for a hotfix while a feature is unfinished, or for parallel tasks.

git worktree add ../hotfix hotfix/payment
git worktree add -b feature/new-ui ../new-ui main
git worktree list
git worktree remove ../hotfix
git worktree prune

A branch can be checked out in only one worktree at a time.

Submodules and subtree

Submodule: link another repository at a fixed commit

git submodule add <repo-url> libs/tool
git clone --recurse-submodules <repo-url>
git submodule update --init --recursive
git submodule update --remote

Subtree: copy another repository's history into a folder

git subtree add --prefix=libs/tool <repo-url> main --squash
git subtree pull --prefix=libs/tool <repo-url> main --squash

A submodule keeps a pointer to a commit, so commit the pointer change after updating it. A subtree needs no extra commands for people who clone the project.

Large repositories: shallow, partial and sparse clones

Shallow clone (latest commit only)

git clone --depth 1 <repo-url>
git fetch --unshallow

Partial clone (download file contents on demand)

git clone --filter=blob:none <repo-url>

Sparse checkout (only some folders in the working directory)

git clone --filter=blob:none --sparse <repo-url>
cd repo
git sparse-checkout set src docs
git sparse-checkout disable

Git LFS (large files)

Git Large File Storage keeps big binary files (design files, videos, datasets) outside the normal history.

git lfs install
git lfs track "*.psd"
git add .gitattributes
git add design.psd
git commit -m "chore: add design file with LFS"
git lfs ls-files

Track patterns before adding the files. Files committed earlier need git lfs migrate import to move into LFS.

Recover lost commits or branches

Git rarely deletes commits right away. The reflog records where HEAD has been, so a "lost" commit after a reset, a bad rebase or a deleted branch can usually be found.

  1. List recent positions of HEAD.
  2. Find the commit you want.
  3. Create a branch there, or reset to it.
git reflog
git switch -c recovered <commit-hash>
git branch recovered HEAD@{3}
git reset --hard HEAD@{1}

Reflog of one branch

git reflog show <branch-name>

Entries expire (90 days by default for reachable commits and 30 days for unreachable ones), so recover promptly.

Line endings on Windows (CRLF vs LF)

Windows uses CRLF, and macOS and Linux use LF. Mixed endings cause noisy diffs and broken shell scripts.

# Windows
git config --global core.autocrlf true

# macOS / Linux
git config --global core.autocrlf input

Better: commit a .gitattributes file so every contributor gets the same behavior

* text=auto
*.sh text eol=lf
*.bat text eol=crlf
*.png binary
*.jpg binary

Apply new rules to files already in the repository

git add --renormalize .
git commit -m "chore: normalize line endings"

Link commits and pull requests to issues (GitHub)

Mention an issue number to link it. A closing keyword closes the issue automatically when the commit or pull request reaches the default branch.

git commit -m "fix: handle empty cart" -m "Fixes #42"
git commit -m "feat: add search filter" -m "Closes #17, closes #18"
  • Keywords: close, closes, closed, fix, fixes, fixed, resolve, resolves, resolved.
  • For an issue in another repository, write Fixes owner/repo#42.
  • Writing #42 without a keyword only links the issue.

rerere (reuse recorded resolution)

Git remembers how you resolved a conflict and applies the same resolution when the same conflict appears again, for example when you rebase a long-running branch several times.

git config --global rerere.enabled true
  1. You resolve a conflict and commit as usual. Git records the conflict and your resolution in .git/rr-cache.
  2. When the same conflict appears later, Git fills in the recorded resolution.
  3. Check the result, then stage the file. With rerere.autoUpdate Git stages it for you.

Inspect and manage

git rerere status
git rerere diff
git rerere remaining
git rerere forget <file>
git rerere gc
git config --global rerere.autoUpdate true

git rerere forget <file> removes a recorded resolution that turned out wrong. Run it while the file is in its conflicted state.

Ignore local changes to a tracked file (skip-worktree)

Tell Git to stop noticing changes in a file that is already tracked, for example a local config file.

git ls-files -v

A pull that changes the file will fail until you undo the flag. A better design is to commit a template such as config.example.php and keep the real file untracked and ignored.

Internals

Objects: blob, tree, commit and tag

Git stores everything as objects in .git/objects. Each object is named by a hash of its content.

ObjectWhat it holdsCreated by
blobThe contents of one file, without its namegit add
treeA folder: names, modes and the blobs or trees insidegit commit
commitA tree, the parent commit(s), author, committer and messagegit commit
tagAn annotated tag: a name, message and the object it points togit tag -a
  • The same content always gives the same hash, so identical files are stored once.
  • A commit hash depends on its tree, parents, author, dates and message. Changing any of them (amend, rebase) creates a new commit.
  • Git 2.29 and later can create SHA-256 repositories with git init --object-format=sha256. Hosting support is still limited.
git cat-file -p HEAD
git cat-file -p "HEAD^{tree}"
git ls-tree HEAD

A commit looks like this

tree 9a4f1c0...
parent 3c1b7e2...
author Name <name@example.com> 1760000000 +0530
committer Name <name@example.com> 1760000000 +0530

feat: add search filter

Inspect objects with cat-file

git cat-file -t HEAD
git cat-file -s HEAD
git cat-file -p HEAD
git cat-file -p HEAD:README.md
git cat-file -e <hash>
  • -t prints the type: blob, tree, commit or tag.
  • -s prints the size in bytes.
  • -p pretty-prints the content.
  • -e only checks that the object exists. The exit code tells you.

Compute a hash, and optionally store the object

git hash-object README.md
git hash-object -w README.md

Refs and HEAD

A branch is a small file that contains a commit hash. Tags live under refs/tags and remote-tracking branches under refs/remotes. HEAD normally points to a branch. In a detached HEAD state it points straight at a commit.

cat .git/HEAD
cat .git/refs/heads/main
git rev-parse HEAD
git rev-parse --abbrev-ref HEAD
git symbolic-ref HEAD
git show-ref
git for-each-ref --format="%(refname:short) %(objectname:short)" refs/heads

Git may store many refs together in .git/packed-refs, so a branch file does not always exist. git symbolic-ref HEAD fails when HEAD is detached.

main@{upstream}, @{u}The upstream branch

git show :/"fix typo"

Plumbing: make a commit by hand

Everyday commands such as add and commit are "porcelain". They are built from small "plumbing" commands. Run this in a throwaway folder with Git Bash to see what git commit does.

git init -b main demo
cd demo
echo "hello" | git hash-object -w --stdin
git update-index --add --cacheinfo 100644,<blob-hash>,hello.txt
git write-tree
echo "Manual commit" | git commit-tree <tree-hash>
git update-ref refs/heads/main <commit-hash>
git log --oneline
  1. hash-object -w stores the file content as a blob and prints its hash.
  2. update-index puts that blob in the staging area under a file name.
  3. write-tree turns the staging area into a tree object.
  4. commit-tree creates a commit that points to the tree.
  5. update-ref moves the branch to the new commit.

Security and good practice

Authentication: SSH keys and tokens

Create an SSH key and test the connection

ssh-keygen -t ed25519 -C "johndoe@example.com"
ssh -T git@github.com

Add the contents of the .pub file to your account settings on the host. Never share the private key (the file without .pub) and protect it with a passphrase.

Use SSH instead of HTTPS for an existing repository

git remote set-url origin git@github.com:<user>/<repo>.git

HTTPS: store credentials in the system credential manager

git config --global credential.helper manager
gh auth login
  • Use a personal access token (PAT) instead of your account password for HTTPS.
  • Give tokens the least permissions and a short expiry.
  • Never put a token in the remote URL, in code or in a committed file.

Signed commits and tags

A signature proves a commit came from you. Hosts show a "Verified" badge. SSH signing is the simplest to set up if you already have an SSH key.

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true

Add the same public key to the host as a signing key, separate from the authentication key.

GPG instead of SSH

gpg --full-generate-key
gpg --list-secret-keys --keyid-format=long
git config --global user.signingkey <KEY-ID>

Sign one commit or tag, and verify

git commit -S -m "feat: signed change"
git tag -s v1.0.0 -m "Release 1.0.0"
git log --show-signature
git verify-commit <commit>

Never commit secrets

Passwords, API keys, tokens, private keys and .env files must never enter history. Once pushed, treat them as leaked.

Prevent

# .gitignore
.env
*.pem
*.key
config/secrets.*
  • Commit a .env.example with placeholder values instead of the real file.
  • Load secrets from environment variables or a secret manager.
  • Enable the host's secret scanning and push protection, and run a scanner such as gitleaks in a pre-commit hook or in CI.

If a secret was committed

  1. Revoke or rotate the secret first. Removing it from history is not enough once it was pushed.
  2. Remove it from history with git filter-repo (a separate tool, replaces the old filter-branch). Run it on a fresh clone.
  3. Force-push the cleaned history and ask collaborators to re-clone.
git filter-repo --path .env --invert-paths
git push --force-with-lease --all

Stop tracking a file that is already committed (keeps history)

git rm --cached .env

Branch protection and CODEOWNERS

On the host (for example GitHub: Settings, then Rules or Branches), protect main so nobody can break it by accident.

  • Require a pull request and at least one approval.
  • Require status checks (tests, lint, build) to pass.
  • Require conversations to be resolved and branches to be up to date.
  • Block force pushes and branch deletion.
  • Optionally require signed commits and a linear history.

CODEOWNERS (.github/CODEOWNERS): request review automatically from the right people

* @my-org/maintainers
/docs/ @my-org/docs-team
*.js @my-org/frontend
/payments/ @alice @bob

Safe force push and history rules

Rewriting commits (amend, rebase, reset) changes their hashes, so the remote needs a force push. This is safe only on your own branches.

git push --force-with-lease
git push --force-with-lease --force-if-includes
  • --force-with-lease refuses to overwrite commits you have not fetched.
  • --force-if-includes also checks that you integrated the remote changes locally.

Rules of thumb

  • Never force-push to main or any shared branch.
  • Rewrite history only for unpushed commits or personal feature branches.
  • On shared history, use git revert instead of reset.
  • Run git status and git diff --staged before committing, and review before pushing.
  • Preview destructive commands first: git clean -nd before git clean -fd.

Supply-chain security

Most attacks arrive through dependencies, build pipelines and stolen accounts, not through your own code.

How do I...?

Undo the last commit

# Keep the changes staged
git reset --soft HEAD~1

# Keep the changes, unstaged
git reset HEAD~1

# Throw the changes away
git reset --hard HEAD~1

If the commit is already pushed and shared, undo it safely with a new commit instead:

git revert HEAD

Change the last commit message

git commit --amend -m "new message"

If it was already pushed to your own branch, update the remote with git push --force-with-lease.

Add a forgotten file to the last commit

git add forgotten-file.txt
git commit --amend --no-edit

Move commits made on the wrong branch

You committed on main but meant to use a feature branch, and nothing is pushed yet.

git switch -c feature/correct-branch
git switch main
git reset --hard origin/main

The new branch keeps your commits, and main goes back to the remote state. Commit or stash uncommitted work first, because --hard discards it.

Squash the last 3 commits into one

git reset --soft HEAD~3
git commit -m "feat: combined change"

Or choose what to combine with git rebase -i HEAD~3 and mark commits as squash. Only do this for commits that are not shared.

Remove a file from all history

git filter-repo --path path/to/file --invert-paths

This rewrites every commit. Run it on a fresh clone, then force-push and ask collaborators to re-clone. If the file contained a secret, rotate the secret first.

Recover a deleted branch

git reflog
git branch recovered-branch <commit-hash>

Find the last commit of the deleted branch in the reflog output and create a branch there.

Make my branch match the remote (discard local work)

git fetch origin
git reset --hard origin/main
git clean -nd
git clean -fd

This deletes local commits and untracked files. Preview with git clean -nd first.

Rename a file only by letter case (Windows)

Windows ignores case, so Git may not see the change. Rename in two steps:

git mv Readme.md tmp.md
git mv tmp.md README.md

Stop tracking a file but keep it

git rm --cached <file>
echo "<file>" >> .gitignore
git commit -m "chore: stop tracking <file>"

See the history of one file

git log --follow -p -- <path>
git log --oneline -- <path>
git blame <path>

Find the commit that added or removed a word

git log -S "search text" --oneline
git log -G "regex" --oneline

-S finds commits that change the number of occurrences. -G finds commits whose changed lines match a regex.

Compare one file between two branches

git diff main..feature -- path/to/file
git show main:path/to/file

Get one file from another branch or commit

git restore --source=<branch-or-commit> -- path/to/file

Update my feature branch with the latest main

git fetch origin
git merge origin/main

# or, for a linear history (own branch only)
git rebase origin/main

Undo a merge

# Not pushed yet
git reset --hard ORIG_HEAD

# Already pushed (1 = keep the first parent, usually main)
git revert -m 1 <merge-commit>

Change the author of the last commit

git commit --amend --reset-author --no-edit
git commit --amend --author="Name <name@example.com>" --no-edit

--reset-author uses your current user.name and user.email.

See what I am about to push

git log origin/main..HEAD --oneline
git diff origin/main..HEAD

Common errors and fixes

You are in 'detached HEAD' state

You checked out a commit or tag instead of a branch. New commits here belong to no branch.

# Keep the work on a new branch
git switch -c my-new-branch

# Or leave without keeping it
git switch main

fatal: refusing to merge unrelated histories

The two repositories do not share a commit, for example a remote created with a README and a separate local project.

git pull origin main --allow-unrelated-histories

Only use it when you are sure you want to join the two histories.

! [rejected] (non-fast-forward) / remote contains work that you do not have

The remote has commits you do not have locally. Integrate them, then push again.

git pull --rebase
git push

Do not force-push to get around this on a shared branch.

Permission denied (publickey)

  1. Test the connection: ssh -T git@github.com.
  2. Check that a key is loaded with ssh-add -l, or add it with ssh-add ~/.ssh/id_ed25519. On Windows, start the "OpenSSH Authentication Agent" service first.
  3. Make sure the matching .pub file is added to your account on the host.
  4. Check that the remote uses SSH: git remote -v.

Authentication failed (HTTPS)

The stored password or token is wrong or expired. Passwords are no longer accepted by most hosts, so use a personal access token.

  • On Windows, open Credential Manager, then Windows Credentials, and remove the entry for the host (for example git:https://github.com). Git asks again on the next push.
  • Or sign in again with gh auth login.

CONFLICT (content): Merge conflict in <file>

Both branches changed the same lines. Follow Resolve merge conflicts, or cancel the merge:

git merge --abort

Unable to create '.git/index.lock': File exists

Another Git process is running, or one crashed. Close other Git tools (editor, GUI client) and retry. If none is running, delete the lock file.

# PowerShell
Remove-Item .git\index.lock

# Git Bash
rm .git/index.lock

fatal: not a git repository

You are outside a repository.

git rev-parse --show-toplevel
cd path/to/your/project

# or start a new repository here
git init

Your local changes would be overwritten by checkout or merge

Save your work first, then switch or merge.

git stash
git switch <branch-name>
git stash pop

Or commit the changes before switching.

Author identity unknown / Please tell me who you are

git config --global user.name "John Doe"
git config --global user.email "johndoe@example.com"

warning: LF will be replaced by CRLF

A harmless line ending notice on Windows. To make the behavior explicit for everyone, add a .gitattributes file. See "Line endings on Windows".

fatal: remote origin already exists

git remote -v
git remote set-url origin <new-url>

error: src refspec main does not match any

There is no commit yet, or your branch has another name.

git branch
git add .
git commit -m "Initial commit"
git branch -M main
git push -u origin main

fatal: The current branch has no upstream branch

git push -u origin <branch-name>

# or set it up automatically for every new branch
git config --global push.autoSetupRemote true

fatal: detected dubious ownership in repository

Common on Windows, for example in C:\wamp64\www, when the folder owner differs from the current user. Mark the folder as safe only if you trust it.

git config --global --add safe.directory C:/wamp64/www/your-project

error: Filename too long (Windows)

git config --global core.longpaths true

File exceeds the 100 MB limit of the host

Large files are rejected by GitHub. Remove the file from the commit, or store it with Git LFS.

# File is only in the last commit
git rm --cached big-file.zip
git commit --amend --no-edit

# File is already deep in history, move it to LFS
git lfs migrate import --include="*.zip"

git lfs migrate rewrites history. Use it on your own branch and coordinate with your team.

Interview questions and answers

How to answer Git interview questions

  • Answer in three parts: what it is, why or when you use it, and the command.
  • Mention the risk when a command rewrites history (reset --hard, rebase, push --force) and the safer option.
  • Use a real example from your work, such as resolving a conflict or recovering a lost commit.
  • Know the pairs interviewers love: merge vs rebase, reset vs revert, fetch vs pull, fork vs clone, Git vs GitHub.
  • Practice in a throwaway repository (see "Practice exercises"), so you can say what you saw, not what you read.
  • If you do not know, explain how you would find out (git help <command>, git reflog, a sandbox clone).

Beginner level questions

What is Git and why do we use it?

Git is a free, open source, distributed version control system. It records the history of changes to files, so you can go back to older versions, see who changed what and why, work on features in separate branches, and collaborate without overwriting each other. Every clone contains the full history, so most commands work offline.

What is the difference between Git and GitHub?

Git is the tool installed on your computer that tracks changes. GitHub is a hosting service for Git repositories that adds pull requests, issues, code review and CI. GitLab and Bitbucket are alternatives. They all use Git underneath.

What is a repository? What is the difference between a local and a remote repository?

A repository stores the files of a project and its complete history in the hidden .git folder. A local repository is on your computer. A remote repository is hosted on a server such as GitHub and shared by the team. Commits move between them with git push, git fetch and git pull.

Explain the working directory, the staging area and the repository.

The working directory holds the files you edit. The staging area (index) holds the changes you selected for the next commit. The repository holds the committed history. git add moves changes from the working directory to the staging area, and git commit moves them into the repository.

What is the difference between git add and git commit?

git add selects changes for the next commit. git commit saves the staged changes as a new snapshot with a message. Nothing is shared with other people until you git push.

git add .
git commit -m "feat: add login form"
git push
What is the difference between git init and git clone?

git init creates a new, empty repository in the current folder. git clone <url> copies an existing repository with its full history and sets origin to the source URL.

What does git status show?

The current branch, the files that are staged, modified but not staged, and untracked, and whether the branch is ahead or behind its upstream. Run it often, especially before git add and git commit.

What is a commit?

A commit is a snapshot of the project at one moment. It has a unique hash, an author, a date, a message and a pointer to its parent commit. Commits form the history of a branch.

How do you view the commit history? 
git log
git log --oneline
git log --oneline --graph --all

--oneline shows one commit per line, and --graph --all draws the branches.

What is a branch and why do we use branches?

A branch is a lightweight, movable pointer to a commit. Branches let you build a feature or fix a bug in isolation without affecting main, and merge the work back when it is ready.

How do you create a branch and switch to it? 
git switch -c feature/login
git checkout -b feature/login

Both do the same. git switch needs Git 2.23 or newer.

What is merging? What is a fast-forward merge?

Merging combines the changes of one branch into another. If the target branch has no new commits, Git just moves its pointer forward. That is a fast-forward merge and it creates no merge commit. If both branches have new commits, Git creates a merge commit with two parents.

What is a merge conflict and how do you resolve it?

A conflict happens when two branches change the same lines, or one branch deletes a file the other edited. Git stops and marks the file with <<<<<<<, ======= and >>>>>>>.

  1. Run git status to see the conflicted files.
  2. Edit each file to the final content and remove the markers.
  3. git add <file>, then git commit (or git merge --continue).

Use git merge --abort to cancel the merge.

What is .gitignore?

A file that lists patterns of files Git should not track, such as node_modules/, .env and build output. It does not affect files that are already tracked. Stop tracking those with git rm --cached <file>.

What is the difference between git fetch and git pull?

git fetch downloads new commits and updates remote-tracking branches such as origin/main, without changing your branch or files. git pull is git fetch followed by a merge (or a rebase) into your current branch.

What is origin?

The default name Git gives to the remote you cloned from. It is only a shortcut for the URL. List your remotes with git remote -v.

What does git push do, and what does -u mean?

It uploads your local commits to a branch on the remote. -u (--set-upstream) links the local branch to the remote branch, so later git push and git pull need no arguments.

git push -u origin feature/login
How do you discard local changes or unstage a file? 
# Discard the edits in a file (cannot be recovered)
git restore <file>

# Unstage a file but keep the edits
git restore --staged <file>
What is HEAD?

HEAD points to the commit you currently have checked out, normally through the current branch. HEAD~1 is its parent. When HEAD points directly to a commit instead of a branch, it is called a detached HEAD.

What is git stash?

It saves your uncommitted changes on a stack and gives you a clean working directory, for example to switch branches. Bring the changes back with git stash pop.

What is the difference between a clone and a fork?

A clone is a Git operation that copies a repository to your computer. A fork is a feature of hosting services such as GitHub: it copies a repository to your own account on the server, so you can change it and propose the changes with a pull request.

How do you set your name and email in Git? 
git config --global user.name "John Doe"
git config --global user.email "johndoe@example.com"

They are stored in every commit you create.

Intermediate level questions

What is the difference between merge and rebase?

Merge joins two branches with a merge commit and keeps the real history. Rebase replays your commits on top of another branch, giving a linear history with new commit hashes.

Rebase your own unpushed branch to stay up to date with main, and merge into shared branches. Do not rebase commits that other people already use. See "merge vs rebase" in the compare section.

What is the difference between reset, revert and restore?
  • reset moves the branch pointer. --soft keeps the changes staged, --mixed (default) keeps them unstaged, and --hard discards them.
  • revert creates a new commit that undoes an earlier commit. It is safe for shared history.
  • restore puts file contents back from the index or a commit and does not move the branch.
Is git reset --hard safe?

No. It permanently discards uncommitted changes in tracked files. Committed work can usually be recovered with git reflog, but uncommitted work cannot. Check git status first and consider git stash.

What does git diff compare? 
git diff            # working directory vs staging area
git diff --staged   # staging area vs last commit
git diff HEAD       # working directory vs last commit
git diff a..b       # two branches or commits
What is git cherry-pick and when do you use it?

It copies the changes of a commit onto the current branch as a new commit. Use it to bring a hotfix to another branch, or when a commit landed on the wrong branch. To bring a whole branch, merge it instead.

git cherry-pick <commit-hash>
What is a detached HEAD and how do you fix it?

HEAD points to a commit instead of a branch, for example after git checkout <hash> or a tag. New commits belong to no branch and can be lost.

# Keep the work
git switch -c rescue-branch

# Or leave without keeping it
git switch main
How do you change the last commit? 
git commit --amend -m "new message"
git add forgotten-file.txt
git commit --amend --no-edit

Amend rewrites the commit. Do not amend commits that are already pushed and shared. On your own branch, push with --force-with-lease.

What is git reflog and how does it help you recover work?

The reflog is a local log of every place HEAD and your branches pointed, including after reset, rebase and branch deletion.

git reflog
git branch recovered <hash>
git reset --hard HEAD@{1}

Entries expire after about 90 days (30 days for unreachable commits), so recover promptly.

How do you squash commits? 
git rebase -i HEAD~3
# change the second and third "pick" to "squash" (or "fixup")

# or, without an editor
git reset --soft HEAD~3
git commit -m "feat: combined change"

Only do this for commits that are not shared.

What are the types of tags in Git?

A lightweight tag is just a name that points to a commit. An annotated tag (-a) is a full object with the tagger, a date and a message, and it can be signed. Use annotated tags for releases. Tags are not pushed by default.

git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0
What are the useful git stash options? 
git stash push -m "message"   # save with a message
git stash push -u             # include untracked files
git stash list
git stash apply               # restore and keep the stash
git stash pop                 # restore and remove the stash
git stash drop stash@{0}
What does git merge --no-ff do?

It always creates a merge commit, even when a fast-forward is possible, so the history shows that a feature branch existed. --ff-only does the opposite: it refuses to merge unless a fast-forward is possible.

What is origin/main?

A remote-tracking branch: a local read-only reference to where main was on origin the last time you fetched. It moves only when you run git fetch, git pull or git push.

How do you handle conflicts during a rebase?

Git stops at the conflicting commit. Resolve the files, stage them, and continue.

git add <file>
git rebase --continue
git rebase --skip     # drop this commit
git rebase --abort    # go back to before the rebase

During a rebase "ours" is the branch you rebase onto and "theirs" is your own commit, the reverse of a merge.

What is the difference between git pull and git pull --rebase?

A plain pull merges the remote commits into your branch and may create a merge commit. git pull --rebase replays your local commits on top of the fetched ones for a linear history. Make it the default with git config --global pull.rebase true.

How do you delete a branch locally and on the remote? 
git branch -d feature/login
git branch -D feature/login          # force, for unmerged work
git push origin --delete feature/login
How do you find who changed a line, or when a change was introduced? 
git blame <file>
git blame -L 10,20 <file>
git log -S "searchText" --oneline
git log -L :functionName:file.c

-S finds commits that added or removed the text.

What is a pull request and how does the review process work?

A pull request asks to merge one branch into another on the host. It shows the diff and lets people comment, request changes, run automatic checks and approve. Typical flow: create a branch, commit, push, open the pull request, address review comments, merge, delete the branch.

Which branching strategies do teams use?
  • GitHub Flow: short-lived feature branches merged to an always deployable main through pull requests.
  • Trunk-based development: very small changes merged to main many times a day, with feature flags and strong CI.
  • Git Flow: long-lived main and develop plus feature, release and hotfix branches, for versioned releases.
How do you undo a commit that was already pushed?

Use git revert, which adds a new commit that undoes the change and keeps history intact for everyone.

git revert <commit-hash>
git push
What is git bisect?

A binary search through history to find the commit that introduced a bug. You mark one good and one bad commit, Git checks out the middle, and you repeat. With git bisect run <script> it is automatic.

git bisect start
git bisect bad
git bisect good v1.4.0
git bisect run ./test.sh
git bisect reset
What are Git hooks?

Scripts that Git runs at certain events, such as pre-commit, commit-msg and pre-push. They are used for linting, tests and commit message rules. The .git/hooks folder is not versioned, so teams share hooks with core.hooksPath, Husky or the pre-commit framework. Newer Git can also define hooks in the config.

Advanced level questions

How does Git store data internally?

Git is a content-addressable object database in .git/objects. Each object is named by the hash of its content. There are four types: blob (file contents), tree (a directory listing of blobs and trees), commit (points to a tree and parent commits, with author and message) and annotated tag.

A commit stores a full snapshot, not a diff. Git later packs similar objects into packfiles with delta compression to save space.

git cat-file -t HEAD
git cat-file -p HEAD
git cat-file -p HEAD^{tree}
What is the index (staging area)?

A binary file, .git/index, that lists the paths, modes and blob hashes that will go into the next commit, plus cached file information for speed. git add writes blobs and updates the index, and git commit writes a tree from it. This is why partial staging with git add -p is possible.

What are refs, and how does HEAD work internally?

Refs map names to commit hashes: refs/heads/* for branches, refs/tags/* for tags and refs/remotes/* for remote-tracking branches. .git/HEAD normally contains ref: refs/heads/main. In a detached HEAD it contains a commit hash.

cat .git/HEAD
git rev-parse HEAD
git for-each-ref
Does Git use SHA-1 or SHA-256?

By default Git names objects with SHA-1, hardened with collision detection. A repository can use SHA-256 with git init --object-format=sha256, but support in hosts and tools is still limited, so SHA-1 remains the norm.

What do git gc, git fsck and git prune do?
  • git gc packs loose objects into packfiles, removes unreachable objects older than the expiry (two weeks by default) and expires old reflog entries.
  • git fsck verifies the integrity of the object database and lists dangling or unreachable objects.
  • git prune deletes unreachable loose objects. It is normally run by gc.
  • git maintenance schedules this kind of upkeep in the background.
How does a three-way merge work?

Git finds the merge base, the best common ancestor (git merge-base A B), and compares both branch tips against it. A change on only one side is taken. The same change on both sides is taken once. Different changes to the same region are a conflict. The default merge strategy is ort since Git 2.34.

What is git rerere?

"Reuse recorded resolution". With rerere.enabled true, Git remembers how you resolved a conflict and applies the same resolution when the same conflict appears again. It helps with long-lived branches and repeated rebases.

git config --global rerere.enabled true
What is git rebase --onto and when do you use it?

It moves a range of commits to a new base. Git takes the commits after <old-base> up to <branch> and replays them on <new-base>. Use it when a branch was started from another feature branch that was later merged or squashed.

git rebase --onto main feature-a feature-b
How do you remove a file or a secret from the entire history?
  1. Rotate or revoke the secret first. Once pushed, it is leaked.
  2. Rewrite history on a fresh clone with git filter-repo (it replaces filter-branch).
  3. Force-push the cleaned history and ask everyone to re-clone.
git filter-repo --path path/to/file --invert-paths
What is the difference between submodules and subtrees?

A submodule stores a pointer to a specific commit of another repository, so people need git submodule update --init and must remember to commit pointer updates. A subtree copies the other repository's content into a folder of your history, so a normal clone just works, but the history becomes larger and updates need git subtree pull.

What are shallow, partial and sparse clones?
  • Shallow (--depth 1): only the latest commits, not the full history.
  • Partial (--filter=blob:none): full history, but file contents are downloaded on demand.
  • Sparse checkout: the full repository, but only some folders are checked out in the working directory.
What is git worktree and why use it?

It creates another working directory linked to the same repository, with its own checked-out branch and index. You can work on several branches at once without stashing or cloning again. A branch can be checked out in only one worktree at a time.

git worktree add ../hotfix -b hotfix main
git worktree remove ../hotfix
What does --force-with-lease do compared to --force?

--force overwrites the remote branch no matter what. --force-with-lease refuses if the remote branch contains commits you have not fetched, so you do not overwrite a teammate's work. --force-if-includes adds a check that you integrated the remote changes locally.

How do signed commits work?

You sign a commit with a GPG or SSH key. The signature proves that the holder of the key created the commit, and hosts show a "Verified" badge when the public key is registered. It does not prove the code is safe.

git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git commit -S -m "feat: signed change"
git log --show-signature
How do you keep a very large repository or monorepo fast?
  • Partial and sparse clones, or scalar clone.
  • core.fsmonitor, core.untrackedCache and git maintenance start.
  • Git LFS for large binary files.
  • Scoped commits, CODEOWNERS per folder and CI that runs only for changed paths.
What is the difference between plumbing and porcelain commands?

Porcelain commands are the user-friendly ones: commit, merge, log. Plumbing commands are low-level building blocks meant for scripts: hash-object, cat-file, update-ref, write-tree, rev-parse. Their output is stable, so scripts can rely on it.

What is a bare repository?

A repository without a working directory. It contains only what is normally inside .git. It is used as a shared central copy that people push to, and hosts store repositories this way.

git init --bare project.git
git clone --bare <url>
What does "reachable" mean and how does it relate to garbage collection?

A commit is reachable when some ref (branch, tag, remote-tracking branch or reflog entry) leads to it. Unreachable objects are kept for a grace period and then removed by git gc. That is why a lost commit can be recovered for weeks, but not forever.

How do you revert a merge commit?

Tell Git which parent is the mainline with -m. Parent 1 is usually the branch you merged into.

git revert -m 1 <merge-commit>

The changes are undone, but Git still treats the branch as merged. To merge the branch again later, first revert the revert.

What is a refspec?

A rule that maps remote refs to local refs. The default fetch refspec is +refs/heads/*:refs/remotes/origin/*: every remote branch is stored as a remote-tracking branch, and + allows updates that are not fast-forwards. You can see it in .git/config.

How do branch protection rules and CODEOWNERS improve a workflow?

Branch protection can require pull requests, approvals, passing checks and a linear history, and can block force pushes and deletion of main. CODEOWNERS automatically requests review from the owners of the changed files. Together they enforce review and quality without relying on discipline.

Scenario and practical questions

You committed on main instead of a feature branch. Nothing is pushed. What do you do? 
git switch -c feature/correct-branch
git switch main
git reset --hard origin/main

The new branch keeps your commits and main goes back to the remote state. Commit or stash uncommitted work first, because --hard discards it.

A teammate pushed a password to the repository. What do you do?
  1. Rotate or revoke the password immediately. Assume it is leaked.
  2. Remove it from history with git filter-repo on a fresh clone, then force-push and ask everyone to re-clone.
  3. Enable secret scanning and push protection, and add the file to .gitignore.
A bad commit is already on main. How do you undo it safely? 
git revert <commit-hash>
git push

Revert adds a new commit, so nobody's history is rewritten. Do not reset and force-push a shared branch.

A bug appeared somewhere in the last 200 commits. How do you find it? 
git bisect start
git bisect bad
git bisect good v1.4.0
git bisect run ./test.sh
git bisect reset

It needs about 8 steps for 200 commits, because each step halves the range.

Your pull request has conflicts with main. What do you do? 
git fetch origin
git rebase origin/main
# resolve each conflict, then
git add <file>
git rebase --continue
git push --force-with-lease

Or merge origin/main into your branch if the team prefers merge commits. Then no force push is needed.

You deleted a branch by mistake. How do you get it back? 
git reflog
git branch feature/login <commit-hash>

Find the last commit of the branch in the reflog output and create the branch there.

git push is rejected with "non-fast-forward". What does it mean?

The remote branch has commits you do not have. Integrate them, then push again. Do not force-push on a shared branch.

git pull --rebase
git push
You are halfway through a feature and need to fix a production bug now. 
# Option 1: stash
git stash push -m "wip feature"
git switch -c hotfix main
# fix, commit, push, then
git switch feature
git stash pop

# Option 2: worktree, no stash needed
git worktree add ../hotfix -b hotfix main
Your branch history is messy. How do you clean it up before the review? 
git rebase -i origin/main
# squash, reword, reorder, drop

# or create fixups while you work
git commit --fixup=<commit>
git rebase -i --autosquash origin/main

Only rewrite commits that are not shared.

Two developers edited the same file. How do you avoid and handle the conflict?

Handle: pull or rebase, resolve the markers together if needed, test, and commit. Avoid: keep branches short-lived, make small pull requests, update from main often, split large files, and use CODEOWNERS and communication for shared areas. rerere helps when the same conflict returns.

Someone force-pushed over your teammates' commits. How do you recover?
  1. Ask everyone to stop pushing and not to run git pull yet.
  2. A teammate who still has the old commits creates a branch from them, for example git branch rescue origin/main before fetching, and pushes it.
  3. Merge or cherry-pick the rescued commits back through a pull request.
  4. Prevent it with branch protection that blocks force pushes.
Cloning the repository takes too long. What can you do? 
git clone --depth 1 <url>
git clone --filter=blob:none --sparse <url>
git sparse-checkout set src docs
git maintenance start

For the repository itself, move large binaries to Git LFS and remove old large files from history.

You committed a 300 MB file and the host rejects the push. 
# Only in the last commit
git rm --cached big-file.zip
git commit --amend --no-edit

# Already deeper in history
git lfs migrate import --include="*.zip"

git lfs migrate rewrites history, so coordinate with your team.

git pull says "Your local changes would be overwritten". What now?

Or commit your changes first. If stash pop conflicts, resolve it like a merge conflict.

A snapshot of the project with a message, an author and a parent.

upstream
Either the remote branch a local branch tracks, or the original repository of a fork.

A local read-only copy of a remote branch, such as origin/main. Updated by git fetch.
Fast-forward
A merge where Git just moves the branch pointer forward because there is no diverging work.
Merge commit
A commit with two parents that joins two lines of history.
Rebase

Cherry-pick

Tag

What's new (Git 2.54 - 2.56)

Latest version

The latest release is Git 2.56.0 (2026-09-28). Check yours with git --version. Commands marked experimental may change in later releases.

git --version
git update-git-for-windows

git history (experimental)

Simple, targeted history rewrites without an interactive rebase. It does not need a to-do list and, except for fixup, does not touch your working tree. It refuses to run if the result would conflict or if the history contains merge commits.

Edit the message of an earlier commit (2.54)

git history reword <commit>

Split a commit into two by choosing hunks (2.54)

git history split <commit>

Fold the staged changes into an earlier commit (2.55)

git add <file>
git history fixup <commit>

Remove a commit and replay its descendants (2.56)

git history drop <commit>

These rewrite history. Do not use them on commits that are already pushed and shared.

git add --resolved (2.56)

Stage only the files that were conflicted in a merge. It refuses to stage any file that still has conflict markers and ignores unrelated local edits, unlike git add -u.

git add --resolved
git add --resolved <pathspec>

git branch --delete-merged (2.56)

Bulk-delete local branches already merged into their upstream. Branches checked out in a worktree or without an upstream are skipped. Preview first with --dry-run.

git branch --delete-merged 'origin/*' 'topic-*' --dry-run
git branch --delete-merged 'origin/*' 'topic-*'

Protect a branch from bulk cleanup

git config branch.<name>.deleteMerged false

Config-based hooks (2.54)

Define hooks in your Git config instead of script files in .git/hooks, so they can be shared across repositories and combined. Several hooks can run for the same event, and a script in .git/hooks still runs last.

[hook "linter"]
	event = pre-commit
	command = ~/bin/linter

[hook "no-leaks"]
	event = pre-commit
	command = ~/bin/leak-detector

List the hooks configured for an event

git hook list pre-commit

Disable one hook without removing it

git config hook.linter.enabled false

Run independent hooks in parallel (2.55)

git config hook.linter.parallel true
git config hook.jobs 4
git hook run -j 4 pre-commit

git refs (2.56)

Low-level reference management. The optional old value protects against overwriting a ref that changed. git refs rename does not update branch configuration the way git branch -m does.

git refs create refs/heads/topic <new-value>
git refs update refs/heads/topic <new-value> [<old-value>]
git refs delete refs/heads/topic [<old-value>]
git refs rename refs/heads/old refs/heads/new

git replay (experimental)

Replay commits onto a new base without touching the working tree. References are now updated atomically by default (2.54).

Reverse the changes of a range of commits (2.54)

git replay --revert <range>

Flatten merge commits into a single line of history (2.56)

git replay --linearize <range>

git rebase --trailer (2.54)

Append a trailer to every rebased commit.

git rebase --trailer "Reviewed-by: A Name <a@example.com>" <upstream>

git bisect run --reset-when-found (2.56)

Clean up the bisect when the culprit is found. The default original returns to the commit checked out before the bisect. found stays on the culprit commit.

git bisect start <bad> <good>
git bisect run --reset-when-found ./test.sh
git bisect run --reset-when-found=found ./test.sh

New git log options

Oldest n commits in a range instead of the newest (2.55)

git log --max-count-oldest=10

Limit the width of the graph; extra lanes show as ~ (2.55)

git log --graph --graph-lane-limit=6

Turn off the new indent of unrelated root commits in the graph (2.56)

git log --graph --no-graph-indent
git config log.graphIndent false

Line history of a function combined with a content search (2.54)

git log -L :function_name:file.c -S search_text --oneline

git log --follow also tracks renames more reliably through merges (2.56).

Push to a group of remotes (2.55)

Push the same branch to several remotes with one name. --atomic is not supported for groups.

git config remotes.publish "github gitlab mirror"
git push publish main

git checkout -m (2.55)

Switch branches and carry your local edits along. If they conflict, Git now saves them in an automatic stash so you can resolve now or reapply later.

git checkout -m <branch-name>

git status against the push remote (2.54)

Show how your branch compares to both its upstream and its push remote, which helps in fork workflows.

git config status.compareBranches "@{upstream} @{push}"

Other small additions

Choose the diff algorithm used by blame (2.54)

git blame --diff-algorithm=histogram <file>

Do not auto-advance to the next file in patch mode (2.54)

git add -p --no-auto-advance

Aliases with any characters, using a subsection (2.54)

[alias "hämta"]
	command = fetch

Maintenance now uses the geometric strategy by default (2.54). Select the old one if you prefer

git maintenance run
git config maintenance.strategy gc

Download missing blobs of a partial clone for a range or paths (2.54, experimental)

git backfill main~100..main
git backfill -- '*.c'

Drop large blobs of a partial clone locally; they are fetched again when needed (2.56)

git repack -a --filter=blob:limit=1m --drop-filtered --dry-run
git repack -a --filter=blob:limit=1m --drop-filtered

Format commit info from standard input (2.55, experimental)

git last-modified | git format-rev --stdin-mode=text --format=%an

Retry on HTTP 429 responses (2.54)

git config http.maxRetries 3
git config http.maxRetryTime 60

Git also masks terminal control characters in remote progress output by default (2.55), and suggests the right syntax for git push origin/main and git branch --set-upstream-to origin main (2.56).
